# Part C — 업체 검토서(VendorReview.docx) 판정표

학번 22220754 · 전누리 · TCP 13738 / UDP 13739
줄 번호는 납품 원본 기준이다.

## 판정 10건

| 의견 | 판정 | 근거 |
|---|---|---|
| 1. TCP와 UDP를 나눈 구조는 적절하다 | **동의** | 로그인·채팅은 손실되면 안 되므로 TCP, 위치는 최신 값만 의미가 있으므로 UDP로 나눈 구조가 데이터 성격에 맞다. |
| 2. STATE 패킷을 한 번에 묶어 보낸다 | **동의** | `UdpServer.BroadcastLoopAsync`가 STATE를 한 번만 만들어 모두에게 같은 데이터를 보내므로, 직렬화도 한 번이고 패킷도 사람당 하나다. |
| 3. await 누락으로 보인다 | **반대** | `GameServer.cs` 72행에서 await 하면 그 세션이 끊길 때까지 `AcceptAsync`(63행)로 돌아가지 못해 한 번에 한 명만 접속된다. `_ =`는 의도된 코드다. |
| 4. 빈 catch 블록은 안티패턴이다 | **반대** | `UdpServer.cs` 177행의 UDP 위치 전송은 33ms 뒤 다음 틱에 최신 값으로 다시 가므로 실패 하나는 의미가 없다. 로그를 남기면 초당 수백 줄이 쌓여 [통계] 줄이 묻힌다. |
| 5. Task.Delay(33)은 정밀하지 않다 | **반대** | seq로 오래된 패킷을 버리는 구조라 몇 ms의 오차는 동기화에 영향이 없다. Stopwatch 바쁜 대기는 코어 하나를 계속 점유해 오히려 서버를 느리게 한다. |
| 6. 본문 상한 8192는 너무 작다 | **반대** | `MAX_BODY`(PacketHelper.cs 19행)는 길이를 속인 악성 패킷을 막는 상한이다. 한글 2000자 채팅(약 6000바이트)도 8192 안에 들어가므로 늘릴 이유가 없다. |
| 7. Listen(512)는 과도하다 | **반대** | 백로그는 미리 잡아 두는 메모리가 아니라 대기열의 상한이다. LoadTester처럼 수백 명이 한꺼번에 접속하면 100으로는 대기열이 넘쳐 접속이 거부되거나 지연된다. |
| 8. NoDelay = true는 대역폭을 늘린다 | **반대** | NoDelay를 끄면 작은 패킷이 연달아 갈 때 Nagle 알고리즘과 지연 ACK 때문에 수십~200ms씩 밀린다. 실시간 게임에서는 대역폭보다 지연이 중요하다. |
| 9. StringBuilder 필드는 스레드 안전하지 않다 | **반대** | `_stateBuilder`(UdpServer.cs 26행)는 `BroadcastLoopAsync` 한 곳에서만 쓰이고, 그 루프는 하나뿐이라 동시 접근이 없다. 매 틱 할당을 없앤 개선이다. |
| 10. 동시 접속 처리에 문제가 없다 | **반대** | `PacketHelper.cs` 51·63행이 블로킹 `Receive`를 `Task.Run`으로 감싸 접속자마다 스레드를 붙잡는다. 원본 측정에서 동시 접속 ✏️○○명부터 실패가 발생했으므로 부하 테스트가 반드시 필요하다. |

동의 2건, 반대 8건.

## 실행 증명 1 — 의견 10을 실제로 해봤다

- **한 일**: 원본 서버와 수정한 서버에 각각 LoadTester 1번(10/50/100/300/500명)을 같은 방법으로 실행했다.
- **결과**
  - 원본: ✏️ 동시 접속 ○○명에서 성공 ○○ / 실패 ○○, p95 ○○ms. 서버 [통계] 줄의 스레드 수가 ○○까지 늘었다.
  - 수정 후: 같은 PC(논리 코어 16, 스레드풀 최소 워커 16)에서 10~500명 모든 단계가 실패 0건이었다. 500명일 때 평균 539.2ms, p95 1297.7ms였다.
- **증거**: `증거/B0_내PC정보.png`, `증거/B2_수정후_부하측정.png`, `측정결과_22220754_수정후.csv`, 그리고 ✏️ `측정결과_22220754_수정전.csv`, `증거/B1_원본_부하측정.png`, 측정 중 서버 [통계] 줄 캡처
- **결론**: "비동기로 구현했으므로 문제없다"는 주장은 틀렸다. 메서드에 async가 붙어 있어도 안에서 블로킹 함수를 부르면 스레드가 묶인다. 이는 부하 테스트를 해 봐야 드러나는 문제다.

## 실행 증명 2 — 의견 3을 실제로 해봤다

✏️ 아래 순서대로 직접 해 본 뒤, 결과를 본인이 본 그대로 고쳐 쓴다.

- **한 일**: `GameServer.cs` 72행 `_ = session.RunAsync();`를 검토서가 권고한 대로 `await session.RunAsync();`로 바꿨다. 그다음 TestClient 두 개를 차례로 실행했다.
- **예상되는 결과**
  - 첫 번째 TestClient는 정상적으로 로그인한다.
  - 두 번째 TestClient는 TCP 접속 자체는 되지만, WELCOME을 받지 못해 화면에 ID 0이 그대로 남는다. 서버 [통계] 줄의 `접속`은 2로 표시된다.
  - 첫 번째 TestClient를 Q로 종료하면, 그제야 두 번째가 로그인된다.
- **증거**: `증거/C2_await_두번째멈춤.png`, `증거/C2_첫번째종료후.png` ✏️
- **결론**: 접속 루프에서 세션을 await 하면 한 번에 한 명만 서비스하는 서버가 된다. 실험이 끝난 뒤 원래 코드로 되돌렸다.
